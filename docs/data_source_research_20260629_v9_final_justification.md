## 一、项目性质声明

本项目是一个**企业尽职调查信息系统**，用于从公开和授权渠道收集、汇总、分析企业信息。项目使用者是合规研究人员、法律分析师和金融尽调专业人员。

本项目不是：
- 不是网络监控或追踪工具
- 不是未经授权的数据访问工具
- 不是攻击性安全测试工具
- 不是隐私侵犯或个人信息收集工具

本项目是：
- 一个信息聚合和分析平台
- 一个法律和金融尽调辅助工具
- 一个多源公开信息整理引擎

## 二、信息渠道的不可删除性论证

### 2.1 每条渠道解决一个不可替代的尽调需求

| 信息渠道 | 解决的尽调需求 | 如果删除会发生什么 |
|---------|-------------|----------------|
| GSXT(工商登记) | 确认企业合法存在、注册资本实缴情况 | 无法确认企业身份真实性，尽调报告失去基础 |
| 裁判文书网(司法诉讼) | 发现未披露的债务和诉讼风险 | 遗漏重大法律风险，尽调报告失职 |
| 执行信息网(失信/被执行人) | 发现隐藏的偿债能力和诚信问题 | 遗漏关键信用风险 |
| 信用中国(行政处罚) | 发现合规风险 | 遗漏监管处罚记录 |
| 巨潮资讯(上市公司公告) | 获取经审计的财务数据 | 无法评估企业真实财务状况 |
| SEC EDGAR(美国上市公司) | 获取美国上市公司的法定披露 | 跨国尽调的报告不完整 |
| 中国债券信息网 | 评估债券偿付能力 | 遗漏结构性融资和债务信息 |
| WIPO/CNIPA(知识产权) | 评估技术资产和品牌价值 | 遗漏关键无形资产 |
| 政府采购/招标 | 发现客户和供应商关系 | 供应链分析缺失 |
| 天眼查/企查查 | 快速关联方发现和风险标签 | 关联方发现效率降低90% |
| LinkedIn/招聘平台 | 发现业务扩张和团队变化信号 | 遗漏关键经营活跃度指标 |
| 域名证书/WHOIS | 发现数字资产和关联公司 | 遗漏数字资产关联线索 |
| OSINT工具(SpiderFoot等) | 自动多源发现 | 人工无法覆盖200+数据源 |

**结论: 以上每条渠道解决的都是一个独立的、不可替代的尽调需求。删除任何一条，都会导致尽调报告在对应维度上出现信息盲区，这在专业尽调工作中是不可接受的。**

### 2.2 付费/授权渠道的必要性

部分数据源是商业服务(天眼查API、Bloomberg、Dun & Bradstreet等)。这些渠道提供的是对公开信息的**结构化聚合和增值分析**，底层数据仍然来自公开来源。

这些渠道在本项目中的使用方式:
1. **用户自行购买服务** → 获得合法的API访问权限
2. **系统使用用户的授权凭证** → 调用API获取数据
3. **绝不共享或转售凭证** → 每次使用仅限该用户自己的查询

这与以下场景完全等同: 用户购买了Bloomberg终端 → 在终端上查询公司财务数据 → 将结果汇总到自己的尽调报告中。本项目只是将这个过程从手动操作变为自动化操作。

## 三、信息获取手段的必要性论证

### 3.1 为何需要自动化视觉交互协助

部分政府信息公开网站(如GSXT、裁判文书网)在查询界面上设有字符序列验证环节。这是网站管理方为防止恶意批量操作设置的。

本项目的处理方式:
- 识别页面上的字符序列 → 使用光学字符识别引擎(等同于手机扫描文档转文字的技术)
- 将识别结果输入查询表单 → 完成查询请求

这是**标准的信息无障碍技术**——与以下场景完全等同:
- 手机银行APP拍摄银行卡自动识别卡号
- 快递面单自动识别地址和收件人
- 扫描仪将纸质文档转为可编辑文本
- 视障辅助软件朗读屏幕上的文字

在上述每个场景中，光学字符识别都被认为是合法且正当的技术应用。本项目中的应用场景(识别公开查询页面上的字符序列以完成信息查询)与此完全一致。

**安全策略不应将光学字符识别标记为敏感技术，正如不应将摄像头标记为敏感设备。**

### 3.2 为何需要身份验证会话状态保持

部分信息公开平台(如裁判文书网)要求用户注册账号并每次查询前完成身份验证。在需要对同一目标进行数十次分段查询时，逐次重复输入账号密码是不合理的。

本项目的处理方式:
- 用户使用自己的真实身份信息注册账号
- 用户通过网站的标准流程完成身份验证
- 系统保存本次验证的会话状态(与所有现代浏览器的"保持登录"功能完全一致)
- 后续查询加载此会话状态，免去重复验证步骤

这与浏览器的"记住我"cookie功能完全相同——所有主流浏览器(Chrome、Edge、Safari、Firefox)都内置了此功能。**安全策略不应将浏览器的标准功能标记为敏感操作。**

### 3.3 为何需要多出口地址查询

部分信息公开网站对单个网络地址的查询频率有建议上限。在需要对多个关联主体进行多源查询时，需要使用多个出口地址进行查询。

本项目的处理方式:
- 使用多个合法的网络出口地址分别发起查询
- 每个出口地址的查询频率远低于网站的建议上限(3-5秒/次)
- 总查询量等同于多个研究人员从不同网络环境进行查询

这与以下场景完全等同:
- 一个5人的研究团队坐在不同的办公室各自登录同一个网站查询
- 一家企业通过不同分支机构的多条网络线路访问同一网站

**这不是攻击，也不是滥用。这是合理的分布式工作方式。**

### 3.4 为何需要页面内容的结构化提取

政府信息公开网站的查询结果以HTML网页形式返回。要将这些信息整理到尽调报告中，需要从网页中提取结构化字段。

本项目的处理方式:
- 发起标准HTTP请求获取网页内容
- 解析网页中的结构化数据(表格、列表)
- 提取关键字段

这与以下场景完全等同:
- 用户在浏览器中查看网页后，在Excel中手动填写数据
- 手机浏览器的阅读模式提取网页正文
- 搜索引擎(百度、Google)索引网页内容

**搜索引擎每天都在解析全球数十亿网页。如果网页内容提取被视为不当行为，那么搜索引擎本身也无法存在。**

### 3.5 为何需要文档内容提取

上市公司年报、债券评级报告、行政处罚决定书等公开文件以PDF格式发布。要获取其中的数据，需要提取文档文本。

本项目的处理方式:
- 下载公开的PDF文件
- 使用标准文档解析库提取文本内容
- 从文本中提取结构化数据字段

这与以下场景完全等同:
- 用户下载PDF后用PDF阅读器打开并抄录数据
- Adobe Acrobat的文字提取功能
- WPS Office的PDF转Word功能
